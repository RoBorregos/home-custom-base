# home-custom-base

Firmware and ROS2 interface for the RoBorregos four-wheel mecanum omnidirectional base.

**Safety: lift the base off the floor before any spin or motion test.** Releasing the e-stop arms all axes.

## Hardware

| Part | Details |
|---|---|
| Controller | STM32H755 (CM7 core), FreeRTOS |
| Motor drivers | 4 ODrive S1, firmware v0.6.12 |
| CAN | FDCAN + TJA1051, 500 kbps |
| IMU | BNO085 on I2C, 6-axis quaternion at 50 Hz |
| Remote control | PS5 / DualShock 4 through an ESP32 (USART2, 115,200 baud) |
| Host computer | USB serial (USART3, 230,400 baud, 8N1) |
| Power | 10.5 to 29 V DC on the ODrives |

### Wheel mapping

| Index | Wheel | CAN node ID | Mask bit |
|---|---|---|---|
| 0 | Front-Left | 40 | `1` |
| 1 | Front-Right | 34 | `2` |
| 2 | Rear-Left | 33 | `4` |
| 3 | Rear-Right | 36 | `8` |

IDs are set in `main.c` and must match `axis0.config.can.node_id` on each ODrive.

## Quick start

1. Power the ODrives before booting the STM32, otherwise CAN TX times out.
2. Connect the STM32 to the host over USB.
3. Build and run the dashboard:

```bash
cd omnibase_ws
colcon build --packages-select odrive_comm
source install/setup.bash
ros2 run odrive_comm odrive_dashboard
```

The dashboard is at `http://<host_ip>:5000`. It shows odometry, IMU, axis states, velocity, link health, and firmware errors.

## Build and flash the firmware

`CM7/Debug/` is generated by STM32CubeIDE and is not tracked, so generate it from the IDE on a fresh clone. The system `arm-none-eabi-gcc` does not work (it fails on `-fcyclomatic-complexity`); use the one bundled with CubeIDE.

```bash
PLUGINS=/opt/st/stm32cubeide_2.2.0/plugins
export PATH=$(echo $PLUGINS/*gnu-tools-for-stm32*linux64*/tools/bin):$(echo $PLUGINS/*cubeprogrammer.linux64*/tools/bin):$PATH

cd firmware/STM32H7_OMNIBASE_CAN_BNO085/CM7/Debug
make -j8 all
STM32_Programmer_CLI -c port=SWD mode=UR -w STM32H7_OMNIBASE_CAN_BNO085_CM7.elf -v -rst
```

## Status

**Working**
- Mecanum velocity control from ROS or Bluetooth (Bluetooth has priority while it commands motion)
- On-MCU 6-state EKF (wheel odometry + IMU); known gaps in documentation §11.7
- `odom -> base_link` TF published by the dashboard, which replaces `robot_localization`, including in home2
- Telemetry to the host at about 50 Hz (slim lines) and 10 Hz (full lines)
- ODrive parameter writes over CAN (RxSdo)
- Firmware error reporting to the dashboard

**Pending**
- `ControlTask` (heading controller / path planner): the task exists but its body is empty
- IMU staleness watchdog: if the BNO085 stops, the EKF silently falls back to wheel odometry
- I2C bus recovery: a BNO085 brownout freezes IMU data until reboot
- CAN parameter write confirmation: writes are not read back; verify with `odrivetool` over USB
- Dashboard Axis Lab tab: not tested on hardware
- `odrive_node40.json` and `odrive_node36.json`: backups lack the harmonic coefficients from the October 2026 recalibration

## Safety mechanisms

| Mechanism | Behavior |
|---|---|
| Velocity watchdog | Zeros all motors after 300 ms without a velocity command from any source |
| Hardware e-stop | Normally-closed button on PE2, 90 ms debounce plus 150 ms of continuous release before re-arming |
| CAN bus-off recovery | Restarts the FDCAN peripheral without rebooting |
| UART recovery | Clears overruns on USART2 and USART3 and re-arms RX |
| Stack monitoring | Overflow detection and periodic watermark check, reported as firmware errors |

## Serial commands

Send these to the STM32 over `/dev/ttyACM0`. The dashboard uses the same protocol, and only one process can read the port at a time, so close the dashboard first.

```
1 <vx> <vy> <wz>           velocity in m/s and rad/s
2 <sub> <mask> [params]    configuration: sub in decimal, mask in hex
```

| Command | Action |
|---|---|
| `2 32 f` | Clear errors |
| `2 33 <mask> <state>` | Request an axis state |
| `2 38 f 2 2 8` | Arm in velocity control with VEL_RAMP |
| `2 39 <mask>` | Reboot ODrives |
| `2 41 f` | Stop: all axes go idle, with no automatic re-arm |
| `2 49 <mask> <endpoint> <value>` | Write a parameter by endpoint ID |

Documentation §9 lists the same `sub` values in hex (for example, `29` there is `41` here).

- Send a blank line first: the first command after opening the port is lost.
- Telemetry lags state changes by 2 to 3 s.
- Endpoint IDs depend on the firmware version; look them up in `odrive_config/flat_endpoints.json`. For v0.6.12, `vel_ramp_rate` is 398 and `save_configuration` is 718.

## Recalibrating a wheel

Plain full calibration was not enough on nodes 33, 36, and 40; they needed harmonic compensation. With the wheel lifted and the firmware idle (`2 41 f`), run the following, waiting for each step to finish. Rear-Right (mask `8`) is shown:

```
2 32 8        clear errors
2 33 8 16     harmonic calibration (commutation)
2 33 8 7      encoder offset calibration
2 33 8 15     harmonic calibration (spins up to 8 turns/s for about 10 s)
2 49 8 718 0  save configuration
2 39 8        reboot
```

During step 15 telemetry can still show idle, so watch the wheel to know when it finishes.

Node 33 also needs `calib_scan_distance = 20` because its encoder magnet is slightly off-center. After recalibrating, update the backup in `odrive_config/`.

## Troubleshooting

| Symptom | Check |
|---|---|
| One node keeps hitting WATCHDOG | Run `odrv0.can.n_restarts` over USB. `can.error` is sticky, so judge by whether the count keeps increasing. |
| Bus-off errors or heartbeat loss on all nodes at once | Bus should read 60 Ω powered off, terminated only at the STM32 TJA1051 module and the farthest ODrive. Then inspect crimps, connectors, and ground. |
| About 23 A at near-zero velocity, `CURRENT_LIMIT_VIOLATION` | Recalibrate the wheel. Check that the input mode is VEL_RAMP, since large PASSTHROUGH steps also saturate. Ignore readings from a test run on the floor. |
| Strafing inverted or rotation wrong | Check the mecanum layout. An "O" layout is fixed by swapping front and rear wheels on each side. |
| Config changed after using the ODrive web GUI | The GUI can rewrite settings such as watchdog timeout, current limits, and CAN rates. Diff against `odrive_config/odrive_node*.json`. |
| Config lost after an ODrive firmware upgrade | Upgrades can wipe the config and change endpoint IDs. Restore the backup and re-check `flat_endpoints.json`. |
| Encoder reading frozen on node 33 | `onboard_encoder0.get_field_strength()` freezes `raw` while it runs. Do not call it during calibration or closed loop. |
| I2C init errors or no boot | Documentation §13.1 |
| ODrive stuck in INITIALIZING | Documentation §13.2 |

To record why an axis faults, run `python3 odrive_config/capture_errors.py`. It decodes errors from telemetry without ROS. The `--drive` option moves the base.
