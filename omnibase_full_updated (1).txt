**Important Notes:**
  - **Baud rate**: 115,200 baud for all serial communication (USART2 and USART3)
  - **Port**: USART3 via USB
  - **Command format**: Send commands as type codes with parameters. Example: "3 0.5 0.0 0.1 0x00" for motion control

### **ODrive CAN Protocol — Message Encoding**

**CAN ID format**: 11-bit standard ID = (NODE_ID << 5) | COMMAND_ID

**Example — Set_Input_Vel (CMD 0x00D):**
  - **CAN ID**: (node_id << 5) | 0x00D
  - **Payload**: bytes 0-3 = velocity (float32, little-endian)
             bytes 4-7 = torque feedforward (float32, little-endian)

**CAN TX safety**: `FDCAN_WAIT_TX_FREE()` macro polls TX FIFO level with a 50 ms hard timeout. If an ODrive is disconnected the task prints "CAN TX timeout" instead of blocking indefinitely.

**CAN RX filter**: accepts ALL standard IDs (mask filter, FilterID1=0x000, FilterID2=0x000). `HAL_FDCAN_RxFifo0Callback()` routes each frame to the correct Axis struct via `node_id = RxHeader.Identifier >> 5`.

# **RTOS**

### **Task Overview and Scheduling**

| Task name | Priority | Stack | Period / blocking behaviour |
|-----------|----------|-------|-----|
| UART_RX_Task | osPriorityHigh | 4 KB | osDelay(5) → ~200 Hz |
| BT_RX_Task | osPriorityHigh | 4 KB | osDelay(5) → ~200 Hz |
| UART_TX_Task | osPriorityNormal | 4 KB | blocks on CAN_2_UTX queue |
| ODriveTask | osPriorityAboveNormal | 4 KB | osDelay(1), telemetry @10ms |
| IMU_Task | osPriorityAboveNormal | 4 KB | osDelay(2) → ~500 Hz poll |
| StartDefaultTask | osPriorityNormal | 512 B | DECLARED BUT NEVER CREATED |
| ControlTask | osPriorityAboveNormal | 1 KB | CREATED, body is empty |

**FreeRTOS Configuration:**
  - **Heap**: 32,768 bytes (heap_4)
  - **Tick rate**: 1,000 Hz (1 ms tick)
  - **HAL timebase**: TIM6 (separate from SysTick — required for FreeRTOS compatibility; SysTick is reserved for RTOS scheduler)

### **UART_RX_Task**

  - USART3, 115,200 baud, PD8=TX, PD9=RX (ROS computer).
  - Uses interrupt + 256-byte ring buffer pattern.
  - Drains ring buffer every 5 ms, assembles lines, calls `UART_RX_ParseLine()` on '\n' or '\r'.
  - High priority ensures ring buffer is drained before it wraps.
  - Parses type-1 (config) and type-2 (velocity) commands from ROS computer.

### **BT_RX_Task**

  - USART2, 115,200 baud, PD5=TX, PD6=RX (ESP32/Bluetooth module).
  - Identical ring-buffer + interrupt pattern (rx_buf2[], rx_char2).
  - Parses "3 <vx> <vy> <wz> <buttons_hex>" messages from Dualshock4 controller.
  - Dead-zones: |vx| < 0.05 m/s → 0, |vy| < 0.05 m/s → 0, |wz| < 0.05 rad/s → 0.
  - Button 0x02 toggles BT off and queues a stop command.
  - BT watchdog code (1 s timeout) exists but is commented out — needs re-enabling for production.

### **UART_TX_Task**

  - Blocks on CAN_2_UTX queue waiting for telemetry messages from ODriveTask.
  - Builds CSV formatted output and transmits via USART3.
  - Sends telemetry at ~100 Hz (every 10 ms from ODriveTask).

### **ODriveTask — State Machine**

**SM_BOOT**: Waits up to 3 s for CFG_STARTUP command or auto-timeout. Calls `ODrive_Startup()` which sends to each of 4 ODrives:
  1. Clear_Errors
  2. Set_Controller_Modes (VELOCITY_CONTROL + PASSTHROUGH)
  3. Set_Axis_Requested_State (CLOSED_LOOP_CONTROL = 8)

**SM_RUNNING**: Every ~1 ms: reads IMU globals (g_bno085_yaw, g_bno085_pitch, g_bno085_roll), polls command queue (2 ms timeout), runs inverse kinematics, sends CAN setpoints to all 4 ODrives. Every 10 ms: updates odometry using forward kinematics, pushes telemetry message to UART_TX_Task.

**SM_IDLE**: All axes → vel=0 then IDLE state. Waits for CFG_STARTUP.

### **IMU_Task**

  - Dedicated task to handle asynchronous BNO085 SHTP (Sensor Hub Transport Protocol) communication.
  - Startup sequence (see BNO085 section for details):
    1. osDelay(500) — avoids printf lock contention at boot
    2. sh2_open() → hal_open(): RST LOW 10 ms, RST HIGH, osDelay(300)
    3. imu_service_ms(200) — drains SHTP advertisement packets
    4. sh2_setSensorCallback(imu_sensor_data_cb, NULL)
    5. imu_service_ms(100) — drains startup control packets
    6. sh2_setSensorConfig(SH2_ROTATION_VECTOR, reportInterval_us=20000) → sensor will now emit a quaternion packet every 20 ms
    7. Main loop: sh2_service() + osDelay(2), forever
  - Continuous polling ensures no SHTP packets are lost.
  - Updates global volatile variables with quaternion and Euler angles.

### **ControlTask**

Scaffolded at osPriorityAboveNormal but body is only `osDelay(10)`. A heading controller or path planner goes here. Currently unused.

# **BNO085**

The BNO085 is a 9-axis IMU with integrated sensor fusion, outputting quaternions in real-time. It replaces the BNO055 due to superior performance and lower latency.

## **Why the sensor was changed**

**BNO055**: Single register-read call, synchronous, ~1 ms per read. No onboard fusion, manual conversion required.

**BNO085**: SHTP (Sensor Hub Transport Protocol) over I2C, asynchronous. The sensor runs internal sensor fusion and pushes quaternion packets to the host at a configured rate (currently 50 Hz / 20 ms interval). Host must call `sh2_service()` continuously to drain packets; there is no "read the angle" register.

## **Why a dedicated IMU_Task is required**

1. **SHTP requires continuous polling** every few ms or packets are lost (ODriveTask can stall for >40 ms during startup or CAN burst sequences).

2. **sh2_open() blocks for ~310 ms** (RST pulse + boot wait). Running this inside ODriveTask would stall CAN for 310 ms, triggering ODrive watchdog errors.

3. **The SH2 library is not re-entrant**; must be called from exactly one task.

4. **Decoupled timing**: IMU at 50 Hz, CAN setpoints at ~1 kHz. Shared volatile globals eliminate any coupling.

5. **Empirical**: Inline BNO085 reads without a dedicated task caused the SHTP session to silently fail after a few seconds due to packet loss.

## **IMU_Task startup sequence (step by step)**

1. `osDelay(500)` — avoids printf lock contention at boot
2. `sh2_open()` → `hal_open()`: RST LOW 10 ms, RST HIGH, `osDelay(300)`
3. `imu_service_ms(200)` — drains SHTP advertisement packets
4. `sh2_setSensorCallback(imu_sensor_data_cb, NULL)`
5. `imu_service_ms(100)` — drains startup control packets
6. `sh2_setSensorConfig(SH2_ROTATION_VECTOR, reportInterval_us=20000)` → sensor will now emit a quaternion packet every 20 ms
7. Main loop: `sh2_service() + osDelay(2)`, forever

## **Data path: INT pin → callback → global variables**

Every ~20 ms BNO085 asserts INT (PD14 LOW). `sh2_service()` calls `hal_read()` which:
  - Checks PD14; if HIGH returns immediately (no I2C traffic).
  - If LOW: reads 4-byte SHTP header, extracts packet length, reads full packet via `HAL_I2C_Master_Receive` (address 0x94).

SH2 layer decodes report → fires `imu_sensor_data_cb()`:
  - `sh2_decodeSensorEvent()` extracts quaternion (w, x, y, z).
  - `q_to_ypr()` converts to yaw, pitch, roll (radians, ZYX convention).
  - Stores in volatile globals: `g_bno085_yaw`, `g_bno085_pitch`, `g_bno085_roll`.

## **Quaternion-to-Euler formulas (euler.c — ZYX convention)**

```
yaw   = atan2(2*i*j - 2*r*k,  2*r² + 2*j² - 1)
pitch = asin (2*j*k + 2*r*i)          [clamped to ±1]
roll  = atan2(-2*i*k + 2*r*j, 2*r² + 2*k² - 1)
```

All in radians. ODriveTask multiplies by 180/π before telemetry.

## **I2C hardware details**

  - **Peripheral**: I2C1 | **Pins**: PB6 (SCL), PB7 (SDA)
  - **BNO085 7-bit address**: 0x4A (8-bit write: 0x94)
  - **INT pin**: PD14 (input, active LOW, polled — not used as MCU interrupt)
  - **RST pin**: PD15 (output, active LOW)

#### **Analysis (PENDIENTE REDACTAR BIEN LO HECHO EN MATLAB)**

Se tiene un marco global {s} y un marco local {b}

La configuración del robot está dada por su posición y ángulo respecto al marco global

q=(θ, x, y)

y su velocidad está dada por:

q̇=(θ̇, ẋ, ẏ)

**Given a desired chassis velocity, what should the driving speeds of the wheels be?**

para cualquier llanta i:
  - Se tiene un centro de la llanta en una posición de (xi, yi) respecto al marco local {b}
  - La dirección en la que gira la llanta está a un ángulo αi respecto a los ejes (xi, yi)
  - Los rodillos permiten movimiento a un ángulo βi respecto a la dirección ⊥ a αi. para una llanta omni i=0

En base a esas definiciones se puede calcular la velocidad de rotación del motor

**Inverse Kinematics (chassis twist → wheel velocities):**

```
u[0] = (vx*(cos+sin) - vy*(cos-sin) + wz*(x_off+y_off)) / r
u[1] = (vx*(cos-sin) + vy*(cos+sin) + wz*(x_off+y_off)) / r
u[2] = (vx*(cos+sin) - vy*(cos-sin) + wz*(x_off+y_off)) / r
u[3] = (vx*(cos-sin) + vy*(cos+sin) - wz*(x_off+y_off)) / r
where cos=cos(phi), sin=sin(phi)
```

ODrive velocity (turns/s at motor shaft):
```
odrive_vel[i] = wheel_sign[i] * u[i] * gear_ratio / (2π)
```

**Forward Kinematics (wheel speeds → robot twist):**

Function: `globalSpeedsFromUMecanum(...)`
Inputs: `u[0..3]` — derived from AXIS_Encoder_Vel / gear_ratio * 2π, corrected for wheel_sign
Outputs: `q_dot[0]=phi_dot` (rad/s), `q_dot[1]=x_dot` (m/s), `q_dot[2]=y_dot` (m/s)
Called inside `ODrive_UpdateTelemetryAndOdometry()` every 10 ms.

**Dead-reckoning odometry:**

```
x     += x_dot   * dt
y     += y_dot   * dt
theta += phi_dot * dt
```

dt computed from `osKernelGetTickCount()` delta.

# **Memory usage investigation**

Se investigó sobre el uso de memoria de la stm usando freertos, pude ver que estaba por default en 15KB total de heap para todas las tasks.  
Aparentemente esto se declara en la sección de .bss (cosas no inicializadas, creo q puestas con 0 por default) del archivo .ld que define el uso de memoria de la stm. La sección .bss está puesta dentro de la memoria RAM_D1.

Investigando vi que puedo ver el uso de memoria con el build analyzer abriendo el archivo .map que se genera cada que se buildea un proyecto. Dado que no parecía estarse usando mucha memoria del RAM_D1, le modifiqué el heap size de FreeRTOSConfig.h a que fuera 64KB, esto esto debería evitar problemas con el stack por un tiempo, ya que ahora es bastante más.  
Si fuese necesario usar más stack, podría aumentarse el tamaño del heap en FreeRTOSConfig.h y/o cambiar el heap_4.c por el heap_5.c del repositorio oficial de FreeRTOS para que el heap sea declarado utilizando secciones de memoria diferentes en diferentes memorias físicas (RAM_D1, RAM_D2, RAM_D3). Sería necesario investigar a profundidad cómo hacer bien esto si fuese necesario.

# **Known Limitations and Future Work**

1. **printf() is not mutex-protected.**
   - MutexUART_DataHandle exists but is never used. If a new task with frequent debug output is added, acquire the mutex around every printf() call.

2. **IMU yaw not fed into inverse kinematics.**
   - phi=0.0 is hardcoded. Passing g_bno085_yaw would enable field-oriented control (commands in a fixed world frame).

3. **ControlTask is empty.**
   - Scaffolded at osPriorityAboveNormal but body is only osDelay(10). A heading controller or path planner goes here.

4. **No I2C bus reset on lockup.**
   - If BNO085 brownout mid-transaction, hal_read() returns SH2_ERR_IO and IMU data freezes. Add SCL toggling + HAL_I2C_Init recovery.

5. **No stack overflow detection.**
   - configCHECK_FOR_STACK_OVERFLOW is not enabled. Set it to 2 in FreeRTOSConfig.h during development.

6. **BNO055 and MCP2515 source files still compiled.**
   - Remove from build to recover ~2–4 KB of flash.

7. **DefaultTask declared but never created.**
   - Its body has an old CAN smoke-test with hard-coded node IDs that conflict with production IDs. Remove or mark clearly as test code.

8. **BT watchdog commented out.**
   - The 1 s timeout that prints a diagnostic when ESP32 goes silent is commented out in BT_RX_Task. Re-enable for production.

  - "Hacer que BT_active sea 1 si conectado y 2 si activo" → Currently BT_active is set to 1 on any valid type-3 packet and cleared to 0 by the toggle button. Add a "connected" state (1) separate from "active/override" (2) and surface it in telemetry.
