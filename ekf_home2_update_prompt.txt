Task
====
Update the home2 stack so the omnibase navigation pipeline consumes the new
on-MCU EKF firmware on the STM32 omnibase, replacing `robot_localization`
entirely.

The firmware now publishes a filtered odometry frame (pose, EKF quaternion,
6×6 covariance, body-frame twist) over UART. The dashboard must build
`nav_msgs/Odometry` from those fields and broadcast `odom → base_link` TF
directly; the launch file must drop the `robot_localization` Node so the two
filters don't collide on the same TF link.

Read first
==========
1. `home-custom-base/ekf_addition.md` — design doc for this rollout.
     - § 4 explains the firmware-side yaw + ω_z sign inversion. The dashboard
       MUST stop negating IMU_yaw / IMU_wz; the firmware does it now, and
       double-inverting silently mirrors the heading.
     - § 5 is the wire format (numeric `i=value` index map; SLIM vs FAT lines).
     - § 8.1 is the dashboard punch list (seven changes).
     - § 8.2 lists what must stay unchanged.
     - § 8.3 covers the launch-file edit + how to keep `/odometry/filtered`
       consumers (Nav2, slam_toolbox) wired up.
2. `home-custom-base/omnibase_ws/src/odrive_comm/odrive_comm/odrive_dashboard.py`
   — working reference implementation of the dashboard changes. The
   omnidriver should end up doing the same things in the same code paths,
   adapted to its own structure (omnidriver has a FAST PATH
   `_publish_imu_odom` that must also be updated).

Edit
====
1. `navigation/packages/omnidriver/omnidriver/odrive_dashboard.py` — apply
   all seven changes in § 8.1.
2. `navigation/packages/omnidriver/package.xml` — add `<exec_depend>tf2_ros
   </exec_depend>` if not already present.
3. `navigation/packages/nav_main/launch/omni_setup/omni_basics.launch.py`
   — remove the `robot_localization` `Node(...)` entry (and any associated
   imports/parameters that no longer have a referent). Make sure downstream
   consumers of `/odometry/filtered` still receive the filtered odometry:
   either remap the omnidriver Node's `/odrive/odom` output to
   `/odometry/filtered` in the same launch file, or confirm by grep that the
   downstream Nav2 / slam_toolbox launches in `omni_setup/` already subscribe
   to `/odrive/odom`. Pick the lower-blast-radius option for the launch
   structure you find.

All dashboard edits must be backward-compatible with the legacy firmware (old
field names, no EKF outputs) — gate each new code path on "is this EKF field
present in the parsed data dict?".

Do NOT
======
- Touch the Dashgo path. `nav_basics.launch.py` and `dashgo_driver/launch/
  ekf.launch.py` keep their own `robot_localization` because the Dashgo base
  has its own fusion config (differential drive, different odom shape). The
  on-MCU EKF only applies to the omnibase.
- Remove the FAST PATH `_publish_imu_odom` shortcut — it's a real perf win;
  just update its field set the same way you update the fat-line build.
- Remove `linear_scale_x` / `linear_scale_y` knobs, the web-socket disconnect
  safety, the IMU outlier rejection in the parser, or the existing CFG_*
  command set / serial protocol.

Verify
======
- `colcon build --packages-select omnidriver nav_main`
- Launch the omnibase navigation stack as it normally runs (`ros2 launch
  nav_main omni_basics.launch.py` or whichever entry point is used).
- `ros2 run tf2_ros tf2_echo odom base_link`
    → live transform updating at ~50 Hz; quaternion changes when the robot
      rotates by hand. Exactly one publisher (no jitter between two filters).
- `ros2 node list | grep robot_localization`
    → empty. The `ekf_node` should not be running for omnibase.
- `ros2 topic echo /odometry/filtered --once` (if downstream still expects
  this topic) OR `ros2 topic echo /odrive/odom --once`:
    → `pose.pose.orientation` is the EKF quaternion (matches IMU yaw, not
      fixed identity).
    → `pose.covariance` and `twist.covariance` diagonals contain
      non-constant values from the firmware (not the legacy 0.02 / 0.08 /
      0.05 placeholders); unestimated slots (z, roll, pitch, vz, wx, wy)
      carry `1e9`.
- Rotate the robot ~90° CCW by hand: `ODOM_phi` (or yaw extracted from the
  quaternion) should grow positive. If it grows negative, a sign-inversion
  has been left in by mistake — see § 4 of the doc.

Report what you changed in <300 words including the colcon build output and
any topic remap you ended up making.
