2. BNO085 — REPLACE THE BNO055 SECTION ENTIRELY
===========================================================================

The PDF index still lists "BNO055" as a section. The firmware no longer
uses the BNO055 at all (the driver files are compiled but never called).
The BNO055 section should be replaced with a BNO085 section covering:

2.1  Why the sensor was changed
  - BNO055: single register-read call, synchronous, ~1 ms per read.
  - BNO085: SHTP (Sensor Hub Transport Protocol) over I2C, asynchronous.
    The sensor runs internal sensor fusion and pushes quaternion packets
    to the host at a configured rate (currently 50 Hz / 20 ms interval).
    Host must call sh2_service() continuously to drain packets; there is
    no "read the angle" register.

2.2  Why a dedicated IMU_Task is required (5 reasons from the .txt)
  Reason 1 — SHTP requires continuous polling every few ms or packets
             are lost (ODriveTask can stall for >40 ms during startup
             or CAN burst sequences).
  Reason 2 — sh2_open() blocks for ~310 ms (RST pulse + boot wait).
             Running this inside ODriveTask would stall CAN for 310 ms,
             triggering ODrive watchdog errors.
  Reason 3 — The SH2 library is not re-entrant; must be called from
             exactly one task.
  Reason 4 — Decoupled timing: IMU at 50 Hz, CAN setpoints at ~1 kHz.
             Shared volatile globals eliminate any coupling.
  Reason 5 — Empirical: inline BNO085 reads without a dedicated task
             caused the SHTP session to silently fail after a few
             seconds due to packet loss.

2.3  IMU_Task startup sequence (step by step)
  1. osDelay(500) — avoids printf lock contention at boot
  2. sh2_open() → hal_open(): RST LOW 10 ms, RST HIGH, osDelay(300)
  3. imu_service_ms(200) — drains SHTP advertisement packets
  4. sh2_setSensorCallback(imu_sensor_data_cb, NULL)
  5. imu_service_ms(100) — drains startup control packets
  6. sh2_setSensorConfig(SH2_ROTATION_VECTOR, reportInterval_us=20000)
     → sensor will now emit a quaternion packet every 20 ms
  7. Main loop: sh2_service() + osDelay(2), forever

2.4  Data path: INT pin → callback → global variables
  Every ~20 ms BNO085 asserts INT (PD14 LOW).
  sh2_service() calls hal_read() which:
    - Checks PD14; if HIGH returns immediately (no I2C traffic).
    - If LOW: reads 4-byte SHTP header, extracts packet length,
      reads full packet via HAL_I2C_Master_Receive (address 0x94).
  SH2 layer decodes report → fires imu_sensor_data_cb():
    - sh2_decodeSensorEvent() extracts quaternion (w, x, y, z).
    - q_to_ypr() converts to yaw, pitch, roll (radians, ZYX convention).
    - Stores in volatile globals: g_bno085_yaw, g_bno085_pitch,
      g_bno085_roll.

2.5  Quaternion-to-Euler formulas (euler.c — ZYX convention)
  yaw   = atan2(2*i*j - 2*r*k,  2*r² + 2*j² - 1)
  pitch = asin (2*j*k + 2*r*i)          [clamped to ±1]
  roll  = atan2(-2*i*k + 2*r*j, 2*r² + 2*k² - 1)
  All in radians. ODriveTask multiplies by 180/π before telemetry.

2.6  I2C hardware details
  Peripheral: I2C1  |  Pins: PB6 (SCL), PB7 (SDA)
  BNO085 7-bit address: 0x4A  (8-bit write: 0x94)
  INT pin: PD14 (input, active LOW, polled — not used as MCU interrupt)
  RST pin: PD15 (output, active LOW)

3. RTOS SECTION — EXPAND FROM BULLET POINTS TO FULL DESCRIPTION
===========================================================================

The PDF RTOS section is 4 bullet-point lists. Add a proper task table and
per-task descriptions:

3.1  Complete Task Table
  Task name         Priority          Stack   Period / blocking behaviour
  ────────────────  ────────────────  ──────  ──────────────────────────
  UART_RX_Task      osPriorityHigh    4 KB    osDelay(5) → ~200 Hz
  BT_RX_Task        osPriorityHigh    4 KB    osDelay(5) → ~200 Hz
  UART_TX_Task      osPriorityNormal  4 KB    blocks on CAN_2_UTX queue
  ODriveTask        osPriorityAboveNormal 4 KB osDelay(1), telemetry @10ms
  IMU_Task          osPriorityAboveNormal 4 KB osDelay(2) → ~500 Hz poll
  StartDefaultTask  osPriorityNormal  512 B   DECLARED BUT NEVER CREATED
  ControlTask       osPriorityAboveNormal 1 KB CREATED, body is empty

  FreeRTOS heap:  32 768 bytes (heap_4)
  FreeRTOS tick:  1 000 Hz (1 ms tick)
  HAL timebase:   TIM6 (separate from SysTick — required for FreeRTOS
                  compatibility; SysTick is reserved for RTOS scheduler)

3.2  UART_RX_Task
  - USART3, 115 200 baud, PD8=TX, PD9=RX (ROS computer).
  - Uses interrupt + 256-byte ring buffer pattern.
  - Drains ring buffer every 5 ms, assembles lines, calls
    UART_RX_ParseLine() on '\n' or '\r'.
  - High priority ensures ring buffer is drained before it wraps.

3.3  BT_RX_Task
  - USART2, 115 200 baud, PD5=TX, PD6=RX (ESP32/Bluetooth module).
  - Identical ring-buffer + interrupt pattern (rx_buf2[], rx_char2).
  - Parses "3 <vx> <vy> <wz> <buttons_hex>" messages.
  - Dead-zones: |vx| < 0.05 m/s → 0, |vy| < 0.05 m/s → 0,
    |wz| < 0.05 rad/s → 0.
  - Button 0x02 toggles BT off and queues a stop command.
  - BT watchdog code (1 s timeout) exists but is commented out.

3.4  ODriveTask — state machine
  SM_BOOT:    Waits up to 3 s for CFG_STARTUP command or auto-timeout.
              Calls ODrive_Startup() which sends to each of 4 ODrives:
                1. Clear_Errors
                2. Set_Controller_Modes (VELOCITY_CONTROL + PASSTHROUGH)
                3. Set_Axis_Requested_State (CLOSED_LOOP_CONTROL = 8)
  SM_RUNNING: Every ~1 ms: reads IMU globals, polls command queue (2 ms
              timeout), runs IK, sends CAN setpoints. Every 10 ms:
              updates odometry, pushes telemetry to UART_TX_Task.
  SM_IDLE:    All axes → vel=0 then IDLE state. Waits for CFG_STARTUP.

  BT priority override: When a BT command arrives, ROS commands are
  discarded for 500 ms. Emergency stop triggered by button bit 3.

  NOTE: IMU yaw is NOT currently fed into inverse kinematics.
  computeNecessaryWheelSpeedsMecanum() is called with phi=0.0.
  The IMU data is telemetry-only at this time.

3.5  ODrive Node ID to Wheel Mapping (addresses To-Do item in PDF)
  odrives[0].NODE_ID = 36,  gear_ratio = 9,  wheel_sign = -1
  odrives[1].NODE_ID = 34,  gear_ratio = 9,  wheel_sign = +1
  odrives[2].NODE_ID = 33,  gear_ratio = 9,  wheel_sign = -1
  odrives[3].NODE_ID = 40,  gear_ratio = 9,  wheel_sign = +1
  Robot geometry: x_offset = 0.3 m, y_offset = 0.3 m, wheel radius = 0.1 m
  (Add FL/BL/FR/BR labels once confirmed — this is the PDF's own To-Do #1)

4. NEW SECTION: FreeRTOS QUEUES AND IPC
===========================================================================

This is entirely absent from the PDF. Add a section covering:

4.1  URX_2_CAN_QueueHandle
  Size: 3 slots of ODriveCmdMsg
  Writers: UART_RX_Task (type-1 and type-2 commands)
           BT_RX_Task   (type-3 BT velocity commands)
  Reader:  ODriveTask   (non-blocking, 2 ms timeout)
  Purpose: Carries robot commands from both command sources to the
           ODrive state machine.

4.2  UART_QueueHandle
  Size: 3 slots of ODriveCmdMsg
  Writer: UART_RX_Task (type-1 velocity commands only)
  Reader: UART_TX_Task (non-blocking, 0 timeout)
  Purpose: Telemetry echo only — not part of control path. Allows
           UART_TX_Task to log the last commanded vx/vy/wz alongside
           actual motor state.

4.3  CAN_2_UTX_QueueHandle
  Size: 3 slots of ODriveTelemetryMsg (~300 bytes each)
  Writer: ODriveTask (every 10 ms)
  Reader: UART_TX_Task (blocking, osWaitForever)
  Purpose: Decouples telemetry assembly from transmission. On queue
           full, ODriveTask drops the oldest entry (drop-oldest policy)
           to ensure UART_TX_Task always gets the freshest data.

4.4  MutexUART_DataHandle
  Created but NEVER acquired or released anywhere in current code.
  Intended as printf() protection across tasks but not implemented.
  Under normal operation this is benign (only UART_TX_Task makes large
  continuous prints). If a new task with frequent debug output is added,
  acquire this mutex around every printf() call.

4.5  Why IMU data uses volatile globals instead of a queue
  g_bno085_yaw, g_bno085_pitch, g_bno085_roll are volatile float globals.
  - 32-bit aligned float write = single STR instruction = atomic on CM7.
  - No partial-write race condition possible.
  - Worst-case data skew: yaw from update N, pitch/roll from N+1 (20 ms).
    Acceptable for telemetry; not acceptable for a heading controller.
  - If strict consistency is required: wrap the three reads in
    taskENTER_CRITICAL() / taskEXIT_CRITICAL().

5. NEW SECTION: UART COMMAND PROTOCOL REFERENCE
===========================================================================

This is entirely absent from the PDF. It is essential for anyone writing
a ROS node or BT firmware to interface with this board.

USART3 (ROS): 115 200 baud, 8N1, PD8/PD9
USART2 (ESP32/BT): 115 200 baud, 8N1, PD5/PD6

From ROS — Type 1 (velocity command):
  "1 <vx> <vy> <wz>\r\n"
  vx, vy in m/s; wz in rad/s.  Commands all four axes.

From ROS — Type 2 (configuration):
  "2 <sub> <mask_hex> [params]\r\n"
  sub=20 0x0F             — clear errors on all axes
  sub=21 0x0F <state>     — set axis state (8 = CLOSED_LOOP)
  sub=22 0x0F <cm> <im>   — set controller + input mode (cm=2=VEL)
  sub=23 0x0F <vl> <cl>   — set velocity limit + current limit
  sub=24 0x0F <pg>        — set position gain
  sub=25 0x0F <vg> <vi>   — set velocity gain + integrator gain
  sub=26 0x0F [cm im st]  — startup sequence (default: cm=2 im=1 st=8)
  sub=27 0x0F             — reboot ODrive
  sub=28 0x0F <tq>        — set input torque
  sub=29 0x0F             — stop (vel→0 then IDLE)
  sub=30 0x0F <pos> <vff> <tff> — set input position with feedforwards

From ESP32/BT — Type 3 (BT velocity command):
  "3 <vx> <vy> <wz> <buttons_hex>\r\n"
  buttons bit 1 (0x02) = toggle BT off + queue stop.
  buttons bit 3 (0x08) = emergency stop.
  Any valid type-3 packet sets BT_active=1.
  BT commands have 500 ms override priority over ROS commands.

7. KINEMATICS SECTION — REPLACE HANDWRITTEN PHOTO WITH TYPED EQUATIONS
===========================================================================

The PDF Code Block Diagram page shows a photograph of handwritten notebook

7.1  Inverse Kinematics (robot twist → wheel speeds)
  Function: computeNecessaryWheelSpeedsMecanum(phi, x_off, y_off, r, u,
                                               phi_dot, y_dot, x_dot)
  Inputs:  vx=x_dot (m/s), vy=y_dot (m/s), wz=phi_dot (rad/s),
           phi = robot heading (currently always 0.0 — IMU not yet used)
  Outputs: u[0..3] — wheel angular velocities in rad/s

  u[0] = (vx*(cos+sin) - vy*(cos-sin) - wz*(x_off+y_off)) / r
  u[1] = (vx*(cos-sin) + vy*(cos+sin) + wz*(x_off+y_off)) / r
  u[2] = (vx*(cos+sin) - vy*(cos-sin) + wz*(x_off+y_off)) / r
  u[3] = (vx*(cos-sin) + vy*(cos+sin) - wz*(x_off+y_off)) / r
  where cos=cos(phi), sin=sin(phi)

  ODrive velocity (turns/s at motor shaft):
    odrive_vel[i] = wheel_sign[i] * u[i] * gear_ratio / (2π)

7.2  Forward Kinematics (wheel speeds → robot twist)
  Function: globalSpeedsFromUMecanum(...)
  Inputs:  u[0..3] — derived from AXIS_Encoder_Vel / gear_ratio * 2π,
           corrected for wheel_sign
  Outputs: q_dot[0]=phi_dot (rad/s), q_dot[1]=x_dot (m/s),
           q_dot[2]=y_dot (m/s)
  Called inside ODrive_UpdateTelemetryAndOdometry() every 10 ms.

7.3  Dead-reckoning odometry
  x     += x_dot   * dt
  y     += y_dot   * dt
  theta += phi_dot * dt
  dt computed from osKernelGetTickCount() delta.

8. ODRIVE CAN PROTOCOL — ADD MESSAGE ENCODING DETAIL
===========================================================================

The PDF shows CAN bus setup screenshots but not the message encoding.
Add a protocol reference subsection under the ODrive CAN section:

  CAN ID format: 11-bit standard ID = (NODE_ID << 5) | COMMAND_ID
  Example — Set_Input_Vel (CMD 0x00D):
    CAN ID:  (node_id << 5) | 0x00D
    Payload: bytes 0-3 = velocity (float32, little-endian)
             bytes 4-7 = torque feedforward (float32, little-endian)

  CAN TX safety: FDCAN_WAIT_TX_FREE() macro polls TX FIFO level with a
  50 ms hard timeout. If an ODrive is disconnected the task prints
  "CAN TX timeout" instead of blocking indefinitely.

  CAN RX filter: accepts ALL standard IDs (mask filter, FilterID1=0x000,
  FilterID2=0x000). HAL_FDCAN_RxFifo0Callback() routes each frame to
  the correct Axis struct via node_id = RxHeader.Identifier >> 5.

10. KNOWN LIMITATIONS AND FUTURE WORK — REPLACE PDF TO-DO WITH TECHNICAL LIST
===========================================================================

The PDF To-Do list has 4 informal items. Replace/supplement with the
following technical breakdown (these are real firmware limitations):

  1. printf() is not mutex-protected.
     MutexUART_DataHandle exists but is never used. If a new task with
     frequent debug output is added, acquire the mutex around every
     printf() call.

  2. IMU yaw not fed into inverse kinematics.
     phi=0.0 is hardcoded. Passing g_bno085_yaw would enable
     field-oriented control (commands in a fixed world frame).

  3. ControlTask is empty.
     Scaffolded at osPriorityAboveNormal but body is only osDelay(10).
     A heading controller or path planner goes here.

  4. No I2C bus reset on lockup.
     If BNO085 brownout mid-transaction, hal_read() returns SH2_ERR_IO
     and IMU data freezes. Add SCL toggling + HAL_I2C_Init recovery.

  5. No stack overflow detection.
     configCHECK_FOR_STACK_OVERFLOW is not enabled. Set it to 2 in
     FreeRTOSConfig.h during development.

  6. BNO055 and MCP2515 source files still compiled.
     Remove from build to recover ~2–4 KB of flash.

  7. DefaultTask declared but never created.
     Its body has an old CAN smoke-test with hard-coded node IDs that
     conflict with production IDs. Remove or mark clearly as test code.

  8. BT watchdog commented out.
     The 1 s timeout that prints a diagnostic when ESP32 goes silent
     is commented out in BT_RX_Task. Re-enable for production.

  (To-Do items from the PDF, mapped to firmware actions:)
  - "Poner comentarios con qué ID es cada motor FL/BL/FR/BR" →
    See section 3.5 above for the current NODE_ID table. Confirm
    wheel positions on the physical robot and add comments to ODriveTask.
  - "Hacer que BT_active sea 1 si conectado y 2 si activo" →
    Currently BT_active is set to 1 on any valid type-3 packet and
    cleared to 0 by the toggle button. Add a "connected" state (1)
    separate from "active/override" (2) and surface it in telemetry.
  - "Hacer que la ESP mande un heartbeat" →
    Requires firmware change on the ESP32 side; MCU side would need
    to decode a heartbeat message type and update a connection flag.
