SECTION 1 — OVERALL PROJECT BEHAVIOR
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1.1  What the project does
--------------------------
This firmware controls a four-wheeled mecanum-drive robot. The four wheels
are each driven by an independent brushless motor through a 9:1 gearbox.
Each motor has its own ODrive motor controller, connected over CAN (FDCAN1,
500 kbps). The MCU acts as the CAN master: it receives high-level robot
velocity commands from two sources (a ROS computer over USART3 and an
ESP32 Bluetooth module over USART2), converts them to individual wheel
speed setpoints using mecanum inverse kinematics, and transmits those
setpoints to each ODrive every ~10 ms.

At the same time the MCU continuously polls the BNO085 9-DOF IMU over I2C
to obtain the robot's orientation (yaw, pitch, roll). The IMU data and
encoder feedback from all four ODrives are bundled into a telemetry packet
and sent back to the ROS computer at ~100 Hz.

In summary the system does four things simultaneously:
  1. Receive and parse robot twist commands (vx, vy, wz) from ROS or BT.
  2. Run mecanum inverse kinematics and send velocity setpoints over CAN.
  3. Receive encoder and status feedback from the ODrives over CAN.
  4. Read orientation from the BNO085 and publish it in the telemetry stream.


1.2  How the subsystems interact
---------------------------------
The block diagram below shows the data paths at a high level.

  ROS (USART3 RX) ──► UART_RX_Task ────────────────────────┐
                                                           │  ODriveCmdMsg
  ESP32 (USART2 RX) ► BT_RX_Task  ────────────────────────►│
                                                           ▼
  BNO085 (I2C1) ──► IMU_Task ──► g_bno085_yaw/pitch/roll ─►│
                                                           │
                            ┌──────────────────────────────┘
                            ▼
                       ODriveTask  ◄──► FDCAN1 ◄──► ODrives (×4)
                            │
                            │  ODriveTelemetryMsg
                            ▼
                       UART_TX_Task ──► USART3 TX ──► ROS

All inter-task communication uses three FreeRTOS message queues.
The BNO085 data is the only piece shared via global variables instead of
a queue (justified because the writes are 32-bit aligned and therefore
atomic on Cortex-M7, and because the IMU task produces data faster than
the telemetry task consumes it — a queue would just add latency).


1.3  BNO055 → BNO085 migration
-------------------------------
The previous version of this firmware used a BNO055 IMU. The BNO055 uses
a simple register map: a single call to bno055_getVectorEuler() issues one
I2C read transaction and immediately returns Euler angles. That call took
about 1 ms and could be inserted anywhere in the ODriveTask main loop
without disrupting timing.

The BNO085 is architecturally very different:

  BNO055: host reads a register address → sensor returns Euler angles.
          One-shot, synchronous, simple.

  BNO085: host and sensor exchange framed packets using the SHTP
          (Sensor Hub Transport Protocol) over I2C. The sensor runs its
          own internal fusion algorithm and pushes reports to the host
          asynchronously whenever data is ready, signalled by the INT pin
          going LOW. The host must continuously service the transport layer
          to drain these packets. There is no register to "read the angle";
          instead the host configures a report (rotation vector at 50 Hz)
          and the sensor sends a new quaternion packet every 20 ms. The
          host must call sh2_service() frequently enough to collect each
          packet before the sensor's internal buffer overflows.

The key practical consequences for firmware design:
  - sh2_service() must be called every few milliseconds, not once per
    control cycle.
  - sh2_open() blocks for ~310 ms during the hardware reset sequence.
  - The SH2 library is not re-entrant; it must be called from exactly one
    task.

These constraints make a dedicated IMU task necessary, as explained in
Section 2 below.

2.2  UART_RX_Task  (start_UART_RX_Task)
---------------------------------------
Purpose: receive text commands from the ROS computer on USART3 (115200 baud,
PD8=TX, PD9=RX).

How it works:
  The task first calls HAL_UART_Receive_IT(&huart3, &rx_char, 1). This
  arms the UART interrupt to receive exactly one byte. Every time a byte
  arrives, the ISR callback HAL_UART_RxCpltCallback() fires, stores the
  byte in a 256-byte ring buffer (rx_buf[]), and immediately re-arms the
  interrupt for the next byte. The task never calls HAL_UART_Receive()
  itself — it only drains the ring buffer in its main loop.

Main loop (every 5 ms via osDelay(5)):
  - Drain rx_buf until head == tail.
  - Accumulate bytes into line_buf until '\n' or '\r'.
  - On line completion, call UART_RX_ParseLine().

This interrupt + ring buffer design means UART_RX_Task never blocks on
actual byte reception. The High priority ensures the ring buffer is drained
before it wraps, even under heavy command traffic.


2.3  BT_RX_Task  (start_BT_RX_Task)
-------------------------------------
Purpose: receive velocity commands from the ESP32 Bluetooth module on
USART2 (115200 baud, PD5=TX, PD6=RX).

How it works: identical ring-buffer + interrupt pattern, using rx_buf2[],
rx_char2, and HAL_UART_Receive_IT(&huart2, ...).

Main loop (every 5 ms):
  - Drain rx_buf2.
  - Parse lines of the format: "3 <vx> <vy> <wz> <buttons_hex>\r\n"
  - Apply dead-zones: |vx| < 0.05 m/s → 0, |vy| < 0.05 m/s → 0,
                      |wz| < 0.05 rad/s → 0.
  - Check button 0x02 (BT_UART_TOGGLE_BUTTON): if set, clear BT_active,
    queue a stop command, and ignore this packet as a velocity command.
  - Otherwise: set BT_active = 1, build an ODriveCmdMsg with
    source = CMD_SOURCE_BT, and put it in URX_2_CAN_QueueHandle.

The BT watchdog (1000 ms timeout) can print a diagnostic message if no data
arrives on USART2 for one second. This code is currently commented out.


2.4  UART_TX_Task  (Start_UART_TX_Task)
-----------------------------------------
Purpose: format and transmit the full telemetry line to the ROS computer
on USART3.

How it works:
  Blocks indefinitely on CAN_2_UTX_QueueHandle (osWaitForever). ODriveTask
  puts a new ODriveTelemetryMsg into this queue every 10 ms, so UART_TX_Task
  wakes up at ~100 Hz.

  On each wake-up:
  1. The telemetry message is received from CAN_2_UTX_QueueHandle.
  2. A non-blocking get from UART_QueueHandle retrieves the most recent
     ROS command (used only for logging CMD_vx/vy/wz in the telemetry).
  3. A single large printf() transmits a comma-separated line containing:
       CMD_vx, CMD_vy, CMD_wz       — last commanded velocities
       IMU_yaw, IMU_roll, IMU_pitch — orientation in degrees
       IK_u0..u3                    — IK-computed wheel speeds (rad/s)
       ODOM_phi, x, y, w, vx, vy   — odometry
       N0..N3, E0..E3, S0..S3, ...  — per-ODrive: node ID, error, state,
                                       controller status, position, velocity,
                                       encoder shadow/CPR, bus voltage/current,
                                       Iq setpoint/measured, updated flag
       BT_active, BT_vx/vy/wz      — Bluetooth override status

  4. osDelay(10) yields the CPU.

Note: printf() in this project retargets to HAL_UART_Transmit(&huart3,...,
HAL_MAX_DELAY) one character at a time (see myprintf.c). This is a
polling, single-threaded UART write. Multiple tasks calling printf()
simultaneously can corrupt output because the UART handle lock
(huart3->Lock) is not protected by an RTOS mutex. In practice, only
UART_TX_Task sends large telemetry bursts while the other tasks only print
diagnostic strings at startup or on error events, so collisions are rare
during normal operation.


2.5  ODriveTask  (StartODriveTask)
------------------------------------
Purpose: run the ODrive state machine, execute inverse kinematics, send
CAN velocity setpoints, update odometry, and push telemetry.

ODrive configuration:
  odrives[0].NODE_ID = 36,  gear_ratio = 9   (front-left or similar)
  odrives[1].NODE_ID = 34,  gear_ratio = 9
  odrives[2].NODE_ID = 33,  gear_ratio = 9
  odrives[3].NODE_ID = 40,  gear_ratio = 9
  wheel_sign = {-1, +1, -1, +1}  (accounts for motor mounting direction)
  Robot geometry: x_offset = 0.3 m, y_offset = 0.3 m, wheel radius = 0.1 m

State machine:

  SM_BOOT   The task waits up to 3000 ms for either:
              - An explicit CFG_STARTUP command from ROS/BT, OR
              - The 3 s auto-start timeout to expire.
            On transition, ODrive_Startup() is called: for each of the 4
            axes it sends Clear_Errors, Set_Controller_Modes
            (VELOCITY_CONTROL + PASSTHROUGH), and Set_Axis_Requested_State
            (CLOSED_LOOP_CONTROL = 8). If any CAN TX fails the boot is
            retried.

  SM_RUNNING  Normal operation. On each iteration (every ~1 ms):
              1. Read latest IMU globals → telemetryMsg.imu.
              2. Try to get a command from URX_2_CAN_QueueHandle (2 ms wait).
              3. If a command arrived, call ODrive_ProcessCommand().
              4. Every 10 ms: call ODrive_UpdateTelemetryAndOdometry() and
                 ODrive_PushLatestTelemetry() to push data to UART_TX_Task.

  SM_IDLE     All axes commanded to IDLE (vel=0 then IDLE state). Waits for
              a CFG_STARTUP command to return to SM_RUNNING.

BT priority override:
  When a command with source == CMD_SOURCE_BT arrives, the task sets
  bt_override_active = 1 and records last_bt_tick. For the next 500 ms,
  any ROS-sourced command is discarded. If no BT command arrives for 500 ms,
  BT override expires and ROS regains control. An emergency stop is
  issued if the BT buttons field bit 3 is set.

IMU data in ODriveTask:
  The task reads the three volatile globals g_bno085_yaw, g_bno085_pitch,
  g_bno085_roll (in radians) written by IMU_Task, multiplies by
  RAD_TO_DEG_D (180/π) and stores them in telemetryMsg.imu. These reads
  are atomic on Cortex-M7 (32-bit aligned load), so no mutex is needed.
  Note: the current IK call uses phi=0.0 (heading not fed back into the
  wheel speed computation). The IMU data is currently telemetry-only.


2.6  IMU_Task  (StartIMUTask)
------------------------------
Purpose: exclusively own the BNO085 and continuously service the SH2/SHTP
protocol stack.

Startup sequence:
  1. osDelay(500) — wait for other AboveNormal tasks to finish printing
     their startup messages (avoids UART lock contention since printf is
     not mutex-protected; see section 4).
  2. printf("IMU_Task: starting BNO085 init")
  3. sh2_open(BNO085_GetHal(), imu_async_event_cb, NULL)
       → calls hal_open(): RST LOW 10 ms, RST HIGH, wait 300 ms for boot
       → sh2 / shtp layer initialises the SHTP advertisement exchange
  4. imu_service_ms(200) — drain the initial SHTP advertisement packets
     (SHTP sends a product ID report on power-up; must be consumed before
     configuring sensors).
  5. sh2_setSensorCallback(imu_sensor_data_cb, NULL) — register the data
     callback that will fire whenever sh2_service() decodes a sensor report.
  6. imu_service_ms(100) — let SHTP process any in-flight control packets.
  7. imu_enable_rotation_vector() — call sh2_setSensorConfig() with
     SH2_ROTATION_VECTOR and reportInterval_us = 20 000 (50 Hz). The BNO085
     will now generate a new quaternion packet every 20 ms.
  8. g_bno085_sensor_ready = 0 (clear any spurious reset flag from startup).
  9. printf("IMU_Task: BNO085 running at 50 Hz")

Main loop (runs indefinitely):
  - sh2_service(): checks if INT pin (PD14) is LOW; if yes, reads the SHTP
    packet over I2C1 via hal_read(), parses the SHTP header and payload,
    and if the payload is a sensor report, fires imu_sensor_data_cb().
    If INT is HIGH (no new packet), sh2_service() returns immediately.
  - Check g_bno085_sensor_ready: if the BNO085 sends a reset event (power
    glitch, brown-out), the async callback sets this flag. The task re-runs
    imu_service_ms(200) and imu_enable_rotation_vector() to reconfigure.
  - osDelay(2): yields CPU for 2 ms. The BNO085 at 50 Hz sends one packet
    every 20 ms, so polling every 2 ms is sufficient — the INT line stays
    HIGH between packets and sh2_service() returns immediately without I2C
    transactions during that time.

Data callback (imu_sensor_data_cb):
  Called from inside sh2_service() when a complete rotation vector report
  has been decoded. Calls sh2_decodeSensorEvent() to parse the quaternion
  fields (real, i, j, k), then calls q_to_ypr() to compute yaw, pitch, roll
  in radians, and stores them in the three volatile globals.


2.7  Why the BNO085 MUST have its own task
-------------------------------------------
This is the core architectural question.

When the previous BNO055 was read inline in ODriveTask, the pattern was:

    /* inside ODriveTask main loop */
    euler = bno055_getVectorEuler();   // one I2C read, ~1 ms, done

The BNO085 cannot be used this way. Here is why in detail:

Reason 1 — The SHTP protocol requires continuous polling.
  The BNO085 queues SHTP packets internally. If the host does not call
  sh2_service() and drain the queue fast enough, older packets are
  overwritten by newer ones. At 50 Hz the sensor produces a packet every
  20 ms. The ODriveTask loop runs every ~1 ms, but during SM_BOOT (the
  3-second startup) and during long CAN TX sequences the loop can stall for
  tens of milliseconds. Any stall longer than ~40 ms risks missing a packet.
  With a dedicated IMU_Task calling sh2_service() every 2 ms, the queue is
  always drained promptly regardless of what ODriveTask is doing.

Reason 2 — sh2_open() blocks for ~310 ms.
  The hal_open() implementation asserts RST for 10 ms and then waits 300 ms
  for the BNO085 to boot. If this ran inside ODriveTask it would stall all
  CAN communication for 310 ms at startup — long enough to cause ODrive
  errors (AXIS_ERROR_WATCHDOG_TIMER_EXPIRED or communication timeout).
  In a dedicated task this blocking call is completely invisible to ODriveTask.

Reason 3 — The SH2 library is not re-entrant.
  The CEVA sh2 library maintains internal state (SHTP sequence counters,
  channel states, callback pointers). The documentation explicitly states
  it must be called from a single thread. If ODriveTask and any other task
  both called sh2_service(), the internal state would be corrupted.

Reason 4 — Decoupled timing.
  The IMU produces data at 50 Hz (every 20 ms). ODriveTask sends CAN
  setpoints every ~1 ms. These two rates have no natural synchronisation.
  Tying the IMU read to the CAN loop would either waste time (reading the
  IMU every 1 ms when there is only new data every 20 ms) or miss data
  (reading only every 20 ms makes the CAN loop jitter if the I2C read
  takes longer than expected). The shared-global approach used here is
  clean: the IMU_Task writes whenever new data arrives; ODriveTask reads
  whenever it needs the latest value, with no blocking and no coupling.

Reason 5 — Previous failed integration.
  Before this architecture was adopted, reading the BNO085 inline without
  a dedicated task caused unreliable behaviour: the SHTP session would
  establish and then silently fail, or the sensor would become
  unresponsive after a few seconds. The root cause was probably Reason 1:
  the ODriveTask loop occasionally stalled long enough for the BNO085's
  internal SHTP state machine to time out. With a dedicated task polling
  every 2 ms this failure mode is eliminated.

SECTION 4 — QUEUES AND RTOS ELEMENTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

4.1  URX_2_CAN_QueueHandle
----------------------------
Created:    osMessageQueueNew(3, sizeof(ODriveCmdMsg), ...)
Writers:    UART_RX_Task (type-1 and type-2 commands)
            BT_RX_Task   (type-3 BT velocity commands)
Readers:    ODriveTask   (non-blocking get, 2 ms timeout)
Purpose:    Carries robot commands from both command sources to the ODrive
            state machine. The 3-slot depth is intentional: if ODriveTask
            is momentarily busy (e.g., doing a multi-message CAN startup
            sequence), up to 3 commands can buffer without being dropped.
            Old commands are not explicitly discarded, but with a 2 ms poll
            interval and a 5 ms command source rate, the queue rarely fills.

ODriveCmdMsg fields used:
  .type         — ODRIVE_CMD_SET_VEL, ODRIVE_CFG_STARTUP, etc.
  .target_mask  — bitmask of which axes (0x0F = all four)
  .source       — CMD_SOURCE_ROS or CMD_SOURCE_BT
  .robot_twist  — [vx (m/s), vy (m/s), wz (rad/s)]
  .buttons      — BT button state (bit 3 = emergency stop)
  (other fields for config commands: axis_state, control_mode, vel_limit…)


4.2  UART_QueueHandle
----------------------
Created:    osMessageQueueNew(3, sizeof(ODriveCmdMsg), ...)
Writers:    UART_RX_Task (type-1 velocity commands only)
Readers:    UART_TX_Task (non-blocking get)
Purpose:    Carries the latest ROS velocity command to UART_TX_Task purely
            for telemetry logging. UART_TX_Task reads it non-blocking (0
            timeout) and prints CMD_vx/vy/wz from it, so the telemetry line
            echoes the last issued command alongside the actual motor state.
            This queue is NOT part of the control path — removing it would
            not affect robot motion, only the completeness of the telemetry.


4.3  CAN_2_UTX_QueueHandle
----------------------------
Created:    osMessageQueueNew(3, sizeof(ODriveTelemetryMsg), ...)
Writers:    ODriveTask (every 10 ms, via ODrive_PushLatestTelemetry())
Readers:    UART_TX_Task (blocking, osWaitForever)
Purpose:    Decouples telemetry assembly (ODriveTask) from telemetry
            transmission (UART_TX_Task). ODriveTask builds the telemetry
            struct at 100 Hz and pushes it; UART_TX_Task wakes up to
            transmit. If the queue is full (UART_TX_Task is slow sending a
            long line), ODrive_PushLatestTelemetry() discards the oldest
            entry and replaces it with the newest — stale telemetry is never
            preferred over fresh telemetry.

ODriveTelemetryMsg is the largest struct in the project (~300 bytes).
It contains: node IDs, per-axis errors/states/velocities/positions/voltages/
currents/encoder shadow+CPR, IK wheel speeds, odometry (phi, x, y, q_dot),
IMU angles, BT status, and a millisecond timestamp.


4.4  MutexUART_DataHandle
--------------------------
Created: osMutexNew(...)
This mutex is created but never explicitly acquired or released anywhere
in the current codebase. It was likely planned as protection for printf()
across tasks but was not implemented. As a result, concurrent printf()
calls from multiple tasks can result in dropped or interleaved characters
(see the osDelay(500) workaround in StartIMUTask). If you add a second
high-output task in the future, use this mutex around all printf() calls.


4.5  Task priorities and why they are chosen
---------------------------------------------
UART_RX_Task and BT_RX_Task run at osPriorityHigh so that received bytes
are drained from their ring buffers before the 256-byte ring wraps under
heavy command traffic. They spend most of their time in osDelay(5), so the
high priority does not starve lower-priority tasks.

ODriveTask and IMU_Task run at osPriorityAboveNormal. They are the two
time-sensitive tasks. They share the same priority and time-slice at 1 ms.
No strict ordering between them is required — each does independent work.

UART_TX_Task runs at osPriorityNormal because transmitting telemetry over
USART3 can tolerate slight latency. Blocking on CAN_2_UTX_QueueHandle
means it sleeps most of the time and wakes precisely when ODriveTask has
new data.

ControlTask (if implemented in the future) is placed at AboveNormal, the
same level as ODriveTask and IMU_Task, so it can preempt telemetry
transmission but not UART command reception.


4.6  The g_bno085_* globals instead of a queue
------------------------------------------------
IMU data is shared between IMU_Task and ODriveTask using three volatile
float globals rather than a queue. This is a deliberate design choice:

  - A 32-bit float write on a 32-bit aligned address is a single STR
    instruction on Cortex-M7 — it is atomic; no partial write is visible.
  - ODriveTask reads the three values within the same telemetry snapshot.
    The worst case is reading yaw from update N and pitch/roll from update
    N+1, a skew of at most 20 ms. This is acceptable for robot telemetry.
  - A queue would add memory overhead, a copy on every write (50 Hz ×
    3 floats), and blocking semantics where none are needed.
  - If strict consistency between yaw, pitch, and roll is ever required
    (e.g., for a heading controller), wrap the three reads in a critical
    section: taskENTER_CRITICAL() / taskEXIT_CRITICAL().

SECTION 5 — IMPORTANT FUNCTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

5.1  BNO085 initialisation: StartIMUTask → sh2_open → hal_open
--------------------------------------------------------------
Call chain on first execution:

  StartIMUTask()
    └─► sh2_open(hal, async_cb, NULL)
          └─► hal->open()  =  hal_open()  [sh2_hal_impl.c]
                  rst_assert()          PD15 → LOW
                  osDelay(10)           10 ms reset pulse
                  rst_deassert()        PD15 → HIGH
                  osDelay(300)          300 ms for BNO085 to boot
                  return SH2_OK
          └─► shtp_open()               initialises SHTP layer
          └─► (SHTP advertisement exchange over I2C)

  imu_service_ms(200)
    loops for 200 ms calling:
      sh2_service()
        └─► shtp_service()
              └─► hal->read()  =  hal_read()
                    if (INT == HIGH) return 0   (no data yet)
                    else:
                      HAL_I2C_Master_Receive 4 bytes  → header
                      extract packetLen from header
                      HAL_I2C_Master_Receive packetLen bytes → payload
                      return packetLen
              delivers packet to sh2 layer
              sh2 layer fires async_cb if it is an async event
              sh2 layer fires sensor_cb if it is a sensor report

  sh2_setSensorCallback(imu_sensor_data_cb, NULL)
    registers the function that will be called for every sensor report

  imu_service_ms(100)
    drains any additional startup control packets

  imu_enable_rotation_vector()
    sh2_setSensorConfig(SH2_ROTATION_VECTOR, {reportInterval_us=20000})
    BNO085 will now send a quaternion report every 20 ms

After this point, the main loop calls sh2_service() + osDelay(2) forever.


5.2  BNO085 data path: INT → callback → globals
-------------------------------------------------
Every ~20 ms the BNO085 asserts its INT pin (PD14 → LOW).

  sh2_service()                        (called from IMU_Task every 2 ms)
    └─► hal_read()                     checks GPIO PD14
          INT is LOW → proceed
          read 4-byte SHTP header      HAL_I2C_Master_Receive(hi2c1, 0x94, hdr, 4)
          extract packetLen            hdr[0] | (hdr[1]<<8), mask 0x7FFF
          read full packet             HAL_I2C_Master_Receive(hi2c1, 0x94, buf, packetLen)
          return packetLen
    └─► SHTP layer assembles packet
    └─► SH2 layer decodes SHTP payload
    └─► identifies report ID = SH2_ROTATION_VECTOR
    └─► imu_sensor_data_cb(cookie, event)
          sh2_decodeSensorEvent(&val, event)
          val.un.rotationVector.real = w (scalar)
          val.un.rotationVector.i   = x
          val.un.rotationVector.j   = y
          val.un.rotationVector.k   = z
          q_to_ypr(w, x, y, z, &yaw, &pitch, &roll)   [euler.c]
          g_bno085_yaw   = yaw    (radians, atan2-based)
          g_bno085_pitch = pitch  (radians, asin-based)
          g_bno085_roll  = roll   (radians, atan2-based)


5.3  q_to_ypr  (Core/Src/sh2/euler.c)
---------------------------------------
Converts a unit quaternion (r=w, i=x, j=y, k=z) to Euler angles using
the ZYX (yaw-pitch-roll) convention:

  yaw   = atan2(2*i*j - 2*r*k,  2*r^2 + 2*j^2 - 1)
  pitch = asin( 2*j*k + 2*r*i)                        (clamped to [-1,1])
  roll  = atan2(-2*i*k + 2*r*j, 2*r^2 + 2*k^2 - 1)

All three angles are returned in radians. ODriveTask multiplies by
RAD_TO_DEG_D (180/π) before inserting into the telemetry message, so the
telemetry output is in degrees (matching the old BNO055 convention).


5.4  CAN message encoding and decoding
----------------------------------------
ODrive CAN protocol: 11-bit standard ID = (NODE_ID << 5) | COMMAND_ID

Transmit (in ODrive.c):
  Set_TX_Param(header, node_id, cmd_id, id_type, frame_type, dlc)
    fills FDCAN_TxHeaderTypeDef: Identifier = (node_id<<5)|cmd_id, DLC, etc.

  Example — Set_Input_Vel(axis, msg, vel, torqueff):
    header.Identifier = (node_id << 5) | 0x00D   (SET_INPUT_VEL)
    data[0..3] = vel  as little-endian float32
    data[4..7] = torqueff as little-endian float32
    HAL_FDCAN_AddMessageToTxFifoQ(&hfdcan1, &header, data)

  FDCAN_WAIT_TX_FREE() macro polls HAL_FDCAN_GetTxFifoFreeLevel() with a
  50 ms hard timeout. This prevents the task from blocking indefinitely if
  an ODrive is disconnected; a "CAN TX timeout" message is printed instead.

Receive (interrupt-driven):
  HAL_FDCAN_RxFifo0Callback() is called by the FDCAN IRQ handler when a
  CAN frame arrives in RX FIFO 0. It reads the frame with
  HAL_FDCAN_GetRxMessage(), extracts node_id = RxHeader.Identifier >> 5,
  finds the matching Axis in the odrives[] array via Find_ODrive_By_NodeID(),
  and calls ODrive_RX_CallBack(axis, &RxHeader, RxData) which uses the
  lower 5 bits of the CAN ID (cmd_id) to update the appropriate Axis fields
  (AXIS_Error, AXIS_Encoder_Vel, AXIS_Bus_Voltage, etc.).

The RX filter in MX_FDCAN1_Init is set to accept ALL standard IDs
(FilterID1=0x000, FilterID2=0x000 with mask filter) so every CAN frame
from any ODrive is received and dispatched to the correct Axis struct.


5.5  computeNecessaryWheelSpeedsMecanum  (main.c)
--------------------------------------------------
Signature:
  computeNecessaryWheelSpeedsMecanum(phi, x_off, y_off, r, u,
                                     phi_dot, y_dot, x_dot)

Computes the required angular velocity (rad/s) for each of the 4 mecanum
wheels given a desired robot twist (vx=x_dot, vy=y_dot, wz=phi_dot) and
the robot's current heading angle phi (currently always 0.0 — the IMU yaw
is not yet fed into the IK).

The kinematic model for a mecanum robot:
  u[0] = (x_dot*(cos+sin) - y_dot*(cos-sin) - phi_dot*(x_off+y_off)) / r
  u[1] = (x_dot*(cos-sin) + y_dot*(cos+sin) + phi_dot*(x_off+y_off)) / r
  u[2] = (x_dot*(cos+sin) - y_dot*(cos-sin) + phi_dot*(x_off+y_off)) / r
  u[3] = (x_dot*(cos-sin) + y_dot*(cos+sin) - phi_dot*(x_off+y_off)) / r
  where cos=cos(phi), sin=sin(phi)

The output u[i] is in rad/s at the wheel. To convert to ODrive velocity
(turns/s at the motor shaft):
  odrive_vel[i] = wheel_sign[i] * u[i] * gear_ratio / (2π)

This is done in ODrive_ProcessCommand() before calling Set_Input_Vel().


5.6  globalSpeedsFromUMecanum  (main.c)
-----------------------------------------
Inverse of the above. Given the 4 measured wheel velocities u[0..3]
(derived from AXIS_Encoder_Vel / gear_ratio * 2π, corrected for wheel sign),
computes the robot's actual body-frame velocities q_dot[0..2]:
  q_dot[0] = phi_dot  (yaw rate, rad/s)
  q_dot[1] = x_dot    (m/s)
  q_dot[2] = y_dot    (m/s)
Called inside ODrive_UpdateTelemetryAndOdometry() every 10 ms.


5.7  ODrive_UpdateTelemetryAndOdometry  (main.c)
-------------------------------------------------
Called by ODriveTask at 100 Hz. Does three things:
  1. Copies all current Axis struct fields into the ODriveTelemetryMsg.
  2. Calls globalSpeedsFromUMecanum() to compute q_dot from encoder velocities.
  3. Dead-reckons odometry: x += q_dot[1]*dt, y += q_dot[2]*dt,
     theta += q_dot[0]*dt, where dt is the time since the last update in
     seconds (computed from osKernelGetTickCount() delta).


5.8  ODrive_PushLatestTelemetry  (main.c)
------------------------------------------
A drop-newest-on-full queue push. Normally puts the telemetry message into
CAN_2_UTX_QueueHandle with a non-blocking put (timeout=0). If the queue is
full (osErrorResource), it discards the oldest message with a non-blocking
get and then puts the new message. This guarantees UART_TX_Task always sees
the most recent data and never blocks ODriveTask.


5.9  UART_RX_ParseLine  (main.c, also in odrive_task_config.c as reference)
----------------------------------------------------------------------------
Parses a null-terminated ASCII line and routes it to the appropriate queue.

Type-1 line: "1 <vx> <vy> <wz>\r\n"
  → sscanf extracts three doubles
  → builds ODriveCmdMsg with type=ODRIVE_CMD_SET_VEL, source=CMD_SOURCE_ROS
  → puts into both UART_QueueHandle (telemetry echo) and URX_2_CAN_QueueHandle

Type-2 line: "2 <sub_type> <mask_hex> [params...]\r\n"
  → sscanf extracts sub_type and hex mask
  → a secondary switch on sub_type parses additional optional parameters
    depending on which configuration command it is (state, ctrl mode, gains,
    limits, etc.)
  → builds ODriveCmdMsg with the appropriate type and parameters
  → puts into URX_2_CAN_QueueHandle only (not the telemetry echo queue)

Any other leading integer prints "Unknown msg_type" and discards the line.


5.10  ODrive_Startup  (main.c)
-------------------------------
Sends the three-message startup sequence to each of the 4 ODrives in order:
  1. Clear_Errors   — clears any latched axis errors (required before
                      attempting state transitions)
  2. Set_Controller_Modes — VELOCITY_CONTROL + PASSTHROUGH input mode
  3. Set_Axis_Requested_State — CLOSED_LOOP_CONTROL (state 8)

FDCAN_WAIT_TX_FREE() is called before each CAN message. If any message fails,
startup is aborted and the state machine remains in SM_BOOT to retry.


5.11  HAL_FDCAN_RxFifo0Callback and Find_ODrive_By_NodeID  (main.c)
--------------------------------------------------------------------
HAL_FDCAN_RxFifo0Callback is the CAN RX interrupt handler. It executes in
interrupt context (not in any task). It:
  1. Reads the frame from FDCAN RX FIFO 0.
  2. Extracts node_id = RxHeader.Identifier >> 5.
  3. Calls Find_ODrive_By_NodeID() which linearly searches the 4-element
     odrives[] array for the matching NODE_ID.
  4. Calls ODrive_RX_CallBack(axis, ...) [ODrive.c] which uses the lower 5
     bits of the CAN ID to update the specific Axis field (e.g.,
     ENCODER_ESTIMATES → AXIS_Encoder_Pos and AXIS_Encoder_Vel).
  5. Sets axis->UPDATED = 1 so ODriveTask can detect fresh data.

Because this runs in ISR context, it must not call any FreeRTOS API or any
function that could block. Writing to the odrives[] array is safe because
ODriveTask only reads odrives[i] inside ODrive_UpdateTelemetryAndOdometry(),
and a single struct field write is atomic on Cortex-M7.

6.3  General firmware infrastructure
--------------------------------------

Core/Src/myprintf.c  +  Core/Inc/myprintf.h
  Retargets the standard C library printf/getchar to USART3 via
  HAL_UART_Transmit/HAL_UART_Receive in blocking (polling) mode with
  HAL_MAX_DELAY. printf sends one character per HAL_UART_Transmit call.
  This is simple and works but is not thread-safe: concurrent calls from
  different tasks can corrupt output because the UART handle lock is not
  an RTOS mutex. For the current project this is acceptable because only
  UART_TX_Task makes frequent, large prints; other tasks only print at
  startup or on error conditions.

Core/Src/stm32h7xx_hal_msp.c
  Hardware-specific peripheral initialisation callbacks called by the HAL
  from within HAL_xxx_Init() functions. Contains:
    HAL_FDCAN_MspInit:  enables FDCAN clock, configures PD0/PD1 as AF9,
                        enables FDCAN1_IT0 IRQ at priority 5.
    HAL_I2C_MspInit:    enables I2C1 clock, configures PB6/PB7 as AF4,
                        enables I2C1 peripheral clock.
    HAL_SPI_MspInit:    enables SPI1 clock, configures PA5/PA6/PB5 as AF5.
                        (SPI1 is initialised but no longer used — BNO085
                        moved to I2C. Harmless to leave in place.)
    HAL_UART_MspInit:   configures USART2 (PD5/PD6, IRQ priority 6) and
                        USART3 (PD8/PD9, IRQ priority 5).
    HAL_TIM_Encoder_MspInit: configures encoder timer pins (TIM1/2/4/8).
    HAL_TIM_PWM_MspInit / HAL_TIM_MspPostInit: configures PWM output pins.

Core/Src/stm32h7xx_hal_timebase_tim.c
  Configures TIM6 as the HAL millisecond timebase, replacing the default
  SysTick. This is necessary because FreeRTOS uses SysTick for its own
  context-switch tick; if HAL also used SysTick the tick counts would
  interfere. TIM6 fires at 1 kHz, calling HAL_IncTick() via
  HAL_TIM_PeriodElapsedCallback() in main.c. This makes HAL_Delay()
  work correctly inside FreeRTOS tasks.

Core/Src/stm32h7xx_it.c
  Interrupt service routines. Contains:
    FDCAN1_IT0_IRQHandler → HAL_FDCAN_IRQHandler (triggers
                            HAL_FDCAN_RxFifo0Callback in main.c)
    USART2_IRQHandler     → HAL_UART_IRQHandler  (triggers
                            HAL_UART_RxCpltCallback, feeds BT ring buffer)
    USART3_IRQHandler     → HAL_UART_IRQHandler  (triggers
                            HAL_UART_RxCpltCallback, feeds ROS ring buffer)
    TIM6_DAC_IRQHandler   → HAL_TIM_IRQHandler   (triggers
                            HAL_TIM_PeriodElapsedCallback → HAL_IncTick)
    HardFault/BusFault/etc. → infinite while(1) loops (no recovery logic)

Core/Src/syscalls.c
  Newlib system call stubs required by the C runtime. Implements _write,
  _read, _sbrk (heap allocator for newlib malloc), and other POSIX-like
  stubs needed for printf, sscanf, malloc, etc. to compile and link.

Core/Inc/FreeRTOSConfig.h
  FreeRTOS configuration constants. Key values:
    configTOTAL_HEAP_SIZE    = 32768  (32 KB)
    configTICK_RATE_HZ       = 1000   (1 ms tick)
    configMAX_PRIORITIES     = 56
    configUSE_PREEMPTION     = 1      (preemptive scheduler)
    configUSE_NEWLIB_REENTRANT = 1    (each task has its own newlib reent
                                       struct — needed for sscanf/printf
                                       to be task-safe)
    configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY = 5
    USE_FreeRTOS_HEAP_4 defined (heap_4 allocator, first-fit with merging)

QUICK REFERENCE: UART COMMAND PROTOCOL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

USART3 (ROS), USART2 (ESP32), 115 200 baud, 8N1

From ROS (USART3):
  Type 1 — velocity command:
    "1 <vx> <vy> <wz>\r\n"
    vx, vy in m/s; wz in rad/s.  All four axes.

  Type 2 — configuration:
    "2 <sub> <mask_hex> [params]\r\n"
    sub=20 0x0F             clear errors on all axes
    sub=21 0x0F <state>     set axis state (e.g. 8=CLOSED_LOOP)
    sub=22 0x0F <cm> <im>   set controller mode (cm=2=VEL) + input mode
    sub=23 0x0F <vl> <cl>   set velocity limit + current limit
    sub=24 0x0F <pg>        set position gain
    sub=25 0x0F <vg> <vi>   set velocity gain + integrator gain
    sub=26 0x0F [cm im st]  startup sequence (default: cm=2 im=1 st=8)
    sub=27 0x0F             reboot ODrive
    sub=28 0x0F <tq>        set input torque (all axes same torque)
    sub=29 0x0F             stop (vel→0 then IDLE state)
    sub=30 0x0F <pos> <vff> <tff>  set input position with feedforwards

From ESP32/BT (USART2):
  Type 3 — BT velocity command:
    "3 <vx> <vy> <wz> <buttons_hex>\r\n"
    buttons bit 1 (0x02) = toggle BT off and queue a stop command.
    Any other valid type-3 packet activates BT_active=1.
    BT commands have 500 ms override priority over ROS commands.

QUICK REFERENCE: TELEMETRY OUTPUT FORMAT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

USART3 TX, 115 200 baud.  One CSV line per 10 ms (100 Hz).

  CMD_vx=, CMD_vy=, CMD_wz=          last commanded robot twist (m/s, rad/s)
  IMU_yaw=, IMU_roll=, IMU_pitch=    BNO085 orientation in DEGREES
  IK_u0..u3=                         IK-computed wheel speeds (rad/s)
  ODOM_phi=, ODOM_x=, ODOM_y=        dead-reckoned pose (rad, m, m)
  ODOM_w=, ODOM_vx=, ODOM_vy=        dead-reckoned body velocities
  N0..N3=  node IDs
  E0..E3=  axis error codes (uint32)
  S0..S3=  axis states
  C0..C3=  controller status
  P0..P3=  position estimates (turns)
  V0..V3=  velocity estimates (turns/s at motor)
  Sh0..Sh3= encoder shadow counts
  CPR0..CPR3= encoder CPR
  Vbus0..Vbus3= bus voltage (V)
  Ibus0..Ibus3= bus current (A)
  IqSet0..IqSet3= Iq setpoint (A)
  IqMeas0..IqMeas3= Iq measured (A)
  U0..U3=  updated flags
  BT_active=, BT_vx=, BT_vy=, BT_wz=  Bluetooth override status

KNOWN LIMITATIONS AND FUTURE WORK
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. printf() is not mutex-protected.
   MutexUART_DataHandle exists but is never used. Under normal operation
   this is benign (only UART_TX_Task does continuous printing), but if a
   new task with frequent debug output is added, acquire the mutex around
   every printf() call to prevent garbled output.

2. IMU yaw not fed into inverse kinematics.
   computeNecessaryWheelSpeedsMecanum() is called with phi=0.0.
   Passing the g_bno085_yaw value would enable field-oriented control
   (commands in a fixed world frame regardless of robot heading).

3. ControlTask is empty.
   A yaw-based heading controller or higher-level path planner could be
   placed in ControlTask (currently just osDelay(10)). Read g_bno085_yaw
   directly for heading feedback and put resulting ODriveCmdMsg into
   URX_2_CAN_QueueHandle.

4. No I2C bus reset on lockup.
   If the I2C bus locks up (e.g., due to a BNO085 brownout mid-transaction),
   hal_read() will return SH2_ERR_IO and the IMU data will freeze. Add I2C
   bus reset logic (toggle SCL manually, call HAL_I2C_Init again) in
   hal_read() to recover automatically.

5. No stack overflow detection.
   configCHECK_FOR_STACK_OVERFLOW is not defined in FreeRTOSConfig.h.
   Enable it (set to 2) during development to catch stack overflows early.

6. BNO055 and MCP2515 files still compiled.
   Remove from build to save ~2–4 KB of flash.

7. DefaultTask is defined but never created.
   Its body contains an old CAN smoke-test loop with hard-coded node IDs
   that conflict with the production IDs in ODriveTask. This function
   should either be removed or clearly marked as a test harness.
