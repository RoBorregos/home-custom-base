============================================================
Connection-status monitoring — reasoning and changes
============================================================

Goal
----
Display the health of the two robot communication links live on the web
dashboard, using elapsed time since the last valid message in each
direction:

  1. ESP32 → STM32  (Bluetooth controller, USART2)
  2. STM32 → PC     (USB-CDC telemetry stream, USART3)

Both links carry their own clocks (the STM32 SysTick and the PC's
monotonic clock), so each side is responsible for measuring the link it
"owns" and the dashboard combines them.

------------------------------------------------------------
Design summary
------------------------------------------------------------

STM32 firmware
  - A new volatile global `g_bt_last_valid_msg_tick` (ms) is updated by
    `start_BT_RX_Task` every time a Type-3 ESP32 line parses successfully.
  - `Start_UART_TX_Task` snapshots that tick once per telemetry packet,
    computes the age via `HAL_GetTick()`, and appends
    `ESP32_age_ms=<n>` to the existing UART line. If no ESP32 message
    has ever been received, the firmware emits `ESP32_age_ms=-1`
    (sentinel — "unknown").
  - All existing telemetry fields, ODrive/IMU/odometry, the watchdog,
    and the BT override behaviour are untouched.

ROS dashboard node (odrive_dashboard.py)
  - On every line read from the STM32 serial port the receiver stamps
    `self._last_raw_msg_time = time.monotonic()` BEFORE running the
    parser, so a malformed line still proves the link is alive.
  - `_parse_and_publish` extracts `ESP32_age_ms` from the regex match
    dict using the existing safe `_si()` helper. -1 (or a missing
    field) is mapped to `None` so the dashboard can show "unknown".
  - A new ROS timer at 4 Hz (`_tick_link_status`) re-emits the latest
    telemetry dict to the web client with refreshed age values, so the
    "STM32→PC" reading keeps growing visibly while the STM32 is silent.
  - A helper `_inject_link_ages(telem)` adds four keys to every emitted
    frame:
        esp32_age_ms / esp32_status   (ESP32→STM32)
        pc_age_ms    / pc_status      (STM32→PC)

Dashboard HTML (assets/dashboard.html)
  - A compact "Links" block is inserted between Odometry and the
    velocity chart in row-1 column-2 of the layout (`.cfgrow` col 2).
  - Two rows: ESP32→STM32 and STM32→PC, each showing the age
    ("123 ms" / "1.42 s" / "unknown") and an OK/WARN/LOST/UNKNOWN pill.
  - JS helpers `fmtAge`, `applyLinkPill`, `updateLink` reuse the
    existing `.pill`, `.pill.run`, `.pill.err` classes plus an inline
    amber style for WARN to match the rest of the dashboard palette.

------------------------------------------------------------
Exact telemetry field added
------------------------------------------------------------

Field name  : ESP32_age_ms
Type        : signed integer, milliseconds
Position    : appended at the end of the existing telemetry line, after
              `BT_active`, `BT_vx`, `BT_vy`, `BT_wz`
Sentinel    : -1  → "no valid ESP32 message has been received since the
                    STM32 booted"
Example     : ...,BT_active=0,BT_vx=0.000,BT_vy=0.000,BT_wz=0.000,
              ESP32_age_ms=123

------------------------------------------------------------
Dashboard widgets modified
------------------------------------------------------------

  HTML element ids touched / introduced
  -------------------------------------
  Existing card  : the row-1 col-2 .card (Odometry / Robot velocity)
  New rows added : ESP32→STM32 line  ids   lnkesp  (age)   lnkespp (pill)
                   STM32→PC    line  ids   lnkpc   (age)   lnkpcp  (pill)

  Status colouring
  ----------------
  OK    (age < 500 ms)        : green pill  (.pill.run)
  WARN  (500 ms ≤ age < 2 s)  : amber pill  (inline style)
  LOST  (age ≥ 2 s)           : red   pill  (.pill.err)
  UNKNOWN  (no message yet)   : muted pill  (default .pill)

  Why these thresholds
  --------------------
  - STM32→PC: `Start_UART_TX_Task` does `osDelay(10)` and is gated by
    `osMessageQueueGet(CAN_2_UTX_QueueHandle, ..., osWaitForever)`,
    so the steady-state rate is ~100 Hz. 500 ms = 50 missed packets
    → unambiguous degradation.
  - ESP32→STM32: in ACTIVE mode the ESP32 streams Type-3 packets at
    ~50 Hz; in PAIRED/INACTIVE it still sends heartbeats well above
    2 Hz. 500 ms covers both rates comfortably.
  - 2 s is the BT watchdog horizon the firmware already uses, so the
    LOST threshold lines up with when the firmware itself starts to
    treat the link as dead.

Validation commands
------------------------------------------------------------

Build + source the workspace:

    cd ~/Github/home-custom-base/omnibase_ws
    colcon build --packages-select odrive_comm
    source install/setup.bash

Run the node:

    ros2 run odrive_comm odrive_dashboard

Verify the raw stream contains the new field:

    ros2 topic echo /odrive/raw --once
    # Expect a line ending with `...,ESP32_age_ms=<n>`

Verify the publish rate (sanity, ~100 Hz with the new 921600 baud):

    ros2 topic hz /odrive/raw

Open the dashboard in a browser at http://localhost:5000 and watch the
two new rows in the Odometry card:
    ESP32→STM32: 35 ms     OK
    STM32→PC:    9 ms      OK

------------------------------------------------------------
Disconnection test scenarios
------------------------------------------------------------

1. ESP32 disconnected / stopped
   - Power off the ESP32 (or unpair the controller).
   - ESP32→STM32 age starts climbing. After ~500 ms it flips to WARN,
     after ~2 s to LOST. The STM32→PC line stays OK because the STM32
     is still publishing telemetry.
   - If the STM32 has never seen an ESP32 message since boot, the line
     reads `unknown / UNKNOWN`.

2. STM32 disconnected / stopped
   - Unplug the STM32 USB cable (or hold reset).
   - The ROS node's serial readline times out; `_last_raw_msg_time`
     stops being refreshed. The 4 Hz timer keeps emitting telemetry,
     so the STM32→PC age climbs visibly on the dashboard
     (OK → WARN → LOST).
   - The ESP32→STM32 field stops updating but the cached value remains
     visible (and will look misleadingly "stale OK" — see notes below).
     The STM32→PC LOST pill is the canonical signal in this case.

3. PC no longer receiving /odrive/raw
   - Equivalent to scenario 2 from the dashboard's perspective.
     Verify with:
         ros2 topic hz /odrive/raw      # should drop to 0
         ros2 topic echo /odrive/raw    # no new lines
   - The web dashboard shows STM32→PC: LOST with an age in seconds.

------------------------------------------------------------
Assumptions and design notes
------------------------------------------------------------

- "Valid ESP32 message" is defined as a successfully sscanf-parsed
  Type-3 line (`parsed >= 4`), regardless of `controll_state` /
  buttons / dead-zones. Heartbeat lines in PAIRED / INACTIVE state are
  intentionally treated as valid so the link can be monitored even
  when nobody is actively driving the robot.

- The firmware-side timestamp uses `HAL_GetTick()` (1 kHz SysTick).
  Wrap-around at ~49.7 days is handled by the unsigned subtraction
  `HAL_GetTick() - bt_tick_snap`. The sentinel `UINT32_MAX` only
  collides ~49.7 days into a boot, at which point the
  "first ESP32 message" check is moot.

- `time.monotonic()` is used on the host so that NTP / system-clock
  jumps cannot make the STM32→PC age go negative or jump backwards.

- During an STM32 disconnect the firmware can't update its own
  ESP32_age_ms, so the dashboard freezes that value at its last
  reported number. We deliberately do NOT extrapolate it on the PC
  (we have no way to know what the firmware would say). The STM32→PC
  LOST pill is the indicator of "you can't trust the ESP32 number any
  more"; treat it as authoritative.

- All parsing uses the existing `_si()` helper, which returns 0 on
  malformed input. We then convert 0/negative to `None` so the
  dashboard shows "unknown" rather than a misleading number. The node
  cannot crash on a truncated `ESP32_age_ms=` field.

- No existing behaviour was removed: every previous telemetry field,
  ROS publisher, IMU/odometry message, BT override logic, command
  watchdog, and ODrive flow continues to work as before. The change
  is purely additive.
